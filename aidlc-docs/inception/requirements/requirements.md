# Requirements — N&C 리딩 어시스턴트

## 1. Intent Analysis

| 항목 | 값 |
|---|---|
| **User Request** | Nielsen & Chuang 교재를 좌측에 띄우고, 읽다가 모르는 부분을 우측 패널에서 질문하면 책과 웹을 근거로 즉시 답변받는 HTML 도구 |
| **Request Type** | New Project (Greenfield) |
| **Scope Estimate** | Multiple Components (뷰어 UI + 로컬 서버 + Claude Code 브리지) |
| **Complexity Estimate** | Moderate |
| **Requirements Depth** | Standard |
| **Clarity (초기)** | Vague — 답변 주체 미정. 명확화 라운드를 거쳐 해소됨 |

### 해결된 핵심 모순
초기 Q1 답변에서 선택지 `D`(자체 Python 에이전트 + Anthropic API 키)와 자유 서술("claude code가 답변하면 돼")이
서로 다른 아키텍처를 가리켰다. 명확화 결과 **Claude Code 자신이 답변 주체**로 확정.
결과적으로 API 키 불필요, 질문당 과금 없음, 책·웹·PDF 이미지 판독 도구를 전부 그대로 활용.

## 3. Functional Requirements

### FR-1 — 책 본문 표시 (좌측) — 2026-08-26 연속 스크롤로 개정
- PDF 원본을 렌더링하여 수식·양자회로도·표가 원본 그대로 보여야 한다
- **연속 스크롤**: 모든 페이지가 세로로 이어져 스크롤만으로 앞뒤를 오간다.
  페이지 경계에서 앞뒤 지면이 함께 보인다
- 710쪽을 다 올리면 200MB가 넘으므로, 자리만 미리 잡고 **화면 근처 페이지만 그린다**
  (실측: DOM에 이미지 3~4장 유지)
- **표시 폭 조절**(40~140%). 줄이면 앞뒤 페이지가 한 화면에 들어온다
- 페이지 이동: 다음/이전, 페이지 번호 직접 입력, 목차·검색·근거 배지 클릭 — 전부 해당 위치로 스크롤
- **질문이 어느 페이지에 속하는지의 판정 규칙**:
  1. 문장이나 영역을 지목했으면 **그 자리의 페이지** (화면 중앙과 달라도 무방)
  2. 아무것도 안 골랐으면 **화면에 가장 넓게 보이는 페이지**
     (중심 거리로 고르면 정확히 반씩 걸친 순간 판정이 임의로 튄다)
  현재 판정된 페이지는 초록 테두리와 입력창 아래 문구로 항상 보여준다
- **책 페이지 번호로 표시한다** (PDF 페이지 아님). 매핑: `pdf page = book page + 34` (검증 완료)
- 출처: `/Users/junho/Desktop/papers/quantum_computing/quantum-computation-and-quantum-information-nielsen-chuang.pdf` (710 pdf pages)

### FR-2 — 추출 텍스트 병행 표시
- 현재 보고 있는 페이지의 추출 텍스트를 **접었다 펼 수 있는** 영역에 표시
- 출처: `refs/nielsen-chuang.txt` (페이지 단위 `\f` 구분)
- **알려진 한계**: 추출 텍스트는 수식 기호가 소실된다 (실측: 책 p.166의 TSP 기호 누락).
  따라서 텍스트는 **보조 수단**이며, 수식의 정본은 항상 FR-1의 PDF 렌더링이다

### FR-3 — 문장 선택 캡처
- 본문에서 드래그하여 선택한 텍스트를 질문에 첨부할 수 있어야 한다
- 선택된 텍스트는 질문 입력란 위에 인용 형태로 미리 보여준다 (무엇이 첨부될지 명확히)
- 선택 해제/취소 가능

### FR-4 — 질문 전송 (우측)
- 자유 입력 텍스트 영역 + 전송
- 전송 시 다음 맥락이 **자동 첨부**된다:
  - 현재 보고 있는 책 페이지 번호
  - FR-3에서 선택한 텍스트 (있는 경우)
- 전송 후 즉시 "답변 대기 중" 상태로 전환

### FR-5 — 답변 표시 (단계적 깊이)
- 답변은 두 층으로 구성된다:
  1. **핵심 요약** — 먼저 보이는 짧은 답
  2. **심화 설명** — "더 자세히" 토글 시 확장. 배경 원리, 왜 그런 결과가 나오는지, 트레이드오프까지
- 답변에는 **근거 출처**가 표시되어야 한다: 책 페이지 번호, 참고한 웹 링크
- 수식이 포함된 답변은 읽을 수 있게 렌더링되어야 한다

### FR-6 — Q&A 기록 축적
- 모든 질문/답변이 마크다운 파일로 영구 저장된다
- 브라우저를 껐다 켜도 이전 대화가 우측 패널에 남아 있다
- 기록에는 타임스탬프와 당시 보던 페이지 번호가 포함된다 (복습 시 맥락 복원)

### FR-7 — 읽던 위치 복원
- HTML을 껐다 다시 켜면 **마지막으로 보던 페이지에서 시작**한다
- 위치는 페이지 이동 시마다 저장된다

### FR-8 — 질문 유실 방지
- 답변 엔진이 즉시 응답하지 못하는 상황에서도 질문은 큐에 적립되고 유실되지 않는다
- UI에 "답변 대기 중 (N건)" 상태가 표시된다
- 엔진이 가용해지면 밀린 질문들이 순차 처리된다
- **주의**: 이 요구사항의 구체적 형태는 OTD-3(§7) 결정에 종속된다.
  헤드리스 호출 방식을 택하면 "오프라인" 상태가 거의 발생하지 않아 큐는 단순 실패 재시도 역할만 한다

### FR-9 — 답변 생성 파이프라인 (Claude Code 측)
질문 파일을 감지하면 Claude Code는 다음을 수행한다:
1. `refs/nc.sh find <keyword>` 로 책 원문에서 관련 페이지 탐색
2. 필요 시 해당 PDF 페이지를 **이미지로 직접 판독** — 수식·회로도가 답변에 필요한 경우 (텍스트 추출로는 소실되므로)
3. **웹 검색은 필요할 때만** (Q5=B): 책만으로 충분하면 생략. 책 범위를 벗어나거나
   2000년 출간 이후의 최신 동향이 필요할 때만 사용
4. FR-5 형식(요약 + 심화 + 출처)으로 답변 파일 작성

### FR-10 — 진행 상황 표시 (2026-08-26 추가)
- 답변을 기다리는 동안 **워커가 실제로 무엇을 하고 있는지** 보여야 한다
- 표시는 **실제 활동에서만** 만든다. 가짜 진행바나 추정 완료 시각을 지어내지 않는다
  - 도구 호출 → `책에서 "X" 검색 중` / `책 p.252 원본 페이지 판독 중` / `웹 검색: X`
  - 도구를 쓰지 않는 구간 → `생각 정리 중` / `답변 작성 중` (+ 누적 토큰)
- 경과 시간을 함께 표시한다. 지나온 단계는 접어서 볼 수 있다
- **근거**: 심화 답변은 실측 3~4분이 걸린다. 그동안 정지 화면은 "느리다"가 아니라
  "고장났다"로 읽힌다. 부수 효과로 워커가 막혔을 때 눈에 보인다

### FR-11 — 본문 검색 (2026-08-26 추가)
- 뷰어 안에서 책 전체를 검색할 수 있어야 한다. 터미널로 나가지 않는다
- 결과에 **책 페이지 번호와 절 이름**을 함께 표시하고, 클릭하면 그 페이지로 이동한다
- 검색 엔진은 이미 있는 `refs/nielsen-chuang.txt` 를 쓴다 (`nc.sh` 와 같은 자료)
- **한계 명시**: 추출 텍스트 기반이므로 수식은 검색되지 않는다

### FR-12 — 목차 네비게이션 (2026-08-26 추가)
- 3단계(장/절/소절) 접이식 목차에서 클릭으로 이동
- 현재 보고 있는 위치의 절이 강조된다
- 출처: `refs/toc-raw.txt` — 233개 항목 (12장/65절/156소절), 부록 포함

### FR-13 — 질문 앵커링과 필터 (2026-08-26 추가)
- 각 질문은 **절(section)에 앵커링**된다. 페이지가 아니다
  - 근거: 한 개념이 여러 쪽에 걸친다 (예: Grover iteration = p.250~255).
    페이지 단위로 묶으면 같은 내용을 읽는 중에도 이전 질문이 보이지 않는다.
    페이지 경계는 조판의 산물이고 절 경계는 의미의 경계다
- **단위를 고정하지 않고 렌즈를 고른다.** 절은 중첩 구조이므로 앵커 하나로 모든 레벨이 나온다
  - `이 페이지` / `이 절` / `이 장` / `전체` — 기본값은 **이 절**
  - 고정 단위는 어디에도 속하지 않는 질문(예: "Grover와 Shor의 차이")을
    질문 당시 서 있던 자리에 잘못 분류한다. 렌즈 방식은 넓히면 해결된다
- **근거 페이지도 색인한다**: 답변의 `bookPages` 에 현재 페이지가 포함되면 그 질문도 보인다
  - `이 페이지 관련` = 여기서 물은 것 ∪ 답변이 이 페이지를 인용한 것
- **절 정보는 저장하지 않고 `bookPage` 로부터 유도한다**
  - 진실의 출처가 목차 하나로 유지되고, 이미 쌓인 질문도 자동으로 앵커가 붙는다

## 4. Non-Functional Requirements

### NFR-1 — 실행 환경
- macOS(darwin), 로컬 전용. `localhost` 바인딩, 외부 노출 없음
- **Python 가상환경 (고정)**: `/Users/junho/venv_folders/qc_env`
  - 인터프리터: `/Users/junho/venv_folders/qc_env/bin/python` (Python 3.13.1, 검증 완료)
  - 이 프로젝트의 모든 Python 실행·설치는 **반드시 이 venv를 사용한다.**
    시스템 `python3` 나 다른 venv를 쓰지 않는다
  - 현재 설치 상태: `pip` 만 존재 (빈 환경). 이는 아래 "표준 라이브러리 우선" 방침과 정합적이다
- Python 3 표준 라이브러리 우선. 무거운 프레임워크 도입 금지
  - 패키지 추가가 불가피할 경우 사전에 근거를 밝히고 위 venv에만 설치한다
- 이미 설치 확인된 외부 도구만 사용: `pdftotext`, `pdfinfo` (poppler)

### NFR-7 — 답변 워커의 규칙 격리 ⭐
- HTML에서 들어오는 질문은 **책에 대한 질문**이지 개발 작업이 아니다.
  따라서 답변 워커는 **AI-DLC 규칙을 로드해서는 안 된다.** AI-DLC는 개발할 때만 사용한다
- **구현 제약**: `CLAUDE.md` 자동 탐색은 상위 디렉터리로 거슬러 올라간다.
  따라서 워커의 작업 디렉터리는 `/Users/junho/coding_work/qc_book` **트리 바깥**이어야 하며,
  `--add-dir` 로 `refs/` 와 PDF 경로만 열어준다
- 워커는 자체의 짧은 "책 튜터" 지침만 갖는다 (FR-5 답변 형식, FR-9 조사 절차)
- **실측 근거**: 동일한 사소한 프롬프트를 프로젝트 루트에서 실행 시 cache-creation **22,759 토큰**,
  프로젝트 트리 바깥에서 실행 시 **13,410 토큰**. 차이 약 9,300 = AI-DLC `CLAUDE.md`
- **`--bare` 는 사용하지 않는다**: 격리 효과는 크지만 인증이 `ANTHROPIC_API_KEY` 로 강제되어
  NFR-5(API 키 미사용, 질문당 과금 없음)를 위반한다

### NFR-2 — 단순성 (YAGNI)
- Q7=A(개인 학습 도구)에 따라: PDF 경로 하드코딩 허용, 멀티 유저/멀티 문서 추상화 금지
- 방어적 코드와 미래 확장 설계를 지양한다
- 재사용이 실제로 필요해지는 시점에 일반화한다

### NFR-3 — 응답성
- 질문 감지는 폴링 지연이 아니라 **파일 감시(watch) 기반 즉시 감지**여야 한다
  (Monitor 도구로 실현 가능함을 확인)
- 체감 지연 = 책·웹 조사 시간뿐. 인위적 대기 없음

### NFR-4 — 데이터 소유
- 모든 데이터(PDF, 추출 텍스트, Q&A 기록)는 로컬에 머문다
- 저작권 있는 교재 전문을 외부 호스팅에 업로드하지 않는다 (Artifact 방식을 배제한 이유)

### NFR-5 — 비용
- 질문당 과금이 발생하지 않아야 한다. Anthropic API 키를 사용하지 않는다

### NFR-6 — 상태 명확성
- 각 질문은 `대기중 / 처리중 / 완료` 중 어느 상태인지 UI에서 항상 알 수 있어야 한다
- Claude Code 세션 연결 여부가 UI에 표시되어야 한다

## 7. Open Technical Decisions (Application Design 단계에서 확정)

**OTD-1 — PDF 렌더링 방식.** FR-1을 만족하는 두 경로가 있으며 트레이드오프가 갈린다:

| 방식 | 장점 | 단점 |
|---|---|---|
| **pdftoppm 서버 사이드 이미지** | 외부 JS 의존성 0, 완전 오프라인, 구현 단순. poppler 이미 설치됨 | 렌더된 이미지 위에서 직접 텍스트 드래그 불가 → FR-3 선택은 텍스트 패널(FR-2)에서 수행 |
| **pdf.js 클라이언트 렌더링** | 페이지 위에서 직접 텍스트 선택 가능 → FR-3이 자연스러움 | ~1MB 라이브러리를 한 번 내려받아 벤더링해야 함 |

NFR-2(YAGNI, 의존성 최소)는 전자를, FR-3의 UX는 후자를 선호한다. Application Design에서 결정한다.

**OTD-2 — 파일 감시 구현.** macOS에는 `inotifywait`가 없다. `fswatch`(미설치 가능성) 대신
짧은 주기 폴링 루프를 Monitor로 감싸는 방식이 무의존성 대안이다. Application Design에서 확정한다.
(OTD-3에서 헤드리스 방식을 택하면 이 결정 자체가 불필요해진다)

**OTD-3 — Claude Code 가용성 확보 방식** ✅ **해결됨 = (a) 헤드리스 호출** (사용자 승인 2026-08-26)

원래 설계는 "Claude Code 세션을 띄워둔다"를 전제했으나, 이는 사람이 창을 관리해야 하는 취약점이다.
조사 결과 **세션을 띄워두지 않는 대안이 실증되었다.**

*검증 결과* (2026-08-26 실측):
- `claude -p '<prompt>' --output-format json --permission-mode dontAsk` → 정상 응답, **3.9초** (TTFT 2.3초)
- 사용 가능 플래그 확인: `-p/--print`, `--output-format json`, `--session-id <uuid>`, `--resume`,
  `--permission-mode`, `--allowedTools`, `--add-dir`, `--bare`
- CLI 경로: `~/.local/bin/claude`
- **측정된 문제점**: 사소한 프롬프트인데도 cache-creation 토큰이 **22,759** 발생.
  원인은 프로젝트의 대형 AI-DLC `CLAUDE.md`가 매 호출마다 자동 로드되는 것.
  답변 워커를 별도 작업 디렉터리에서 실행하고 `--add-dir`로 `refs/`만 열어주면 해소된다

| | (a) 헤드리스 호출 (`claude -p`) | (b) 상시 세션 + 파일 감시 |
|---|---|---|
| 띄워둘 것 | **미니 서버만** (브라우저만 열면 됨) | 미니 서버 + **Claude Code 터미널 창** |
| 사람의 관리 | 불필요 | 창을 닫으면 멈춤 |
| 질문당 지연 | 시작 오버헤드 ~2.3초 + 조사 시간 | 시작 오버헤드 없음, 조사 시간만 |
| 대화 맥락 | `--session-id` 고정으로 유지 가능 | 자연스럽게 유지됨 |
| 컨텍스트 낭비 | 호출마다 재로드 (별도 cwd로 완화) | 한 번 로드 후 재사용 |
| FR-8 큐 | 사실상 불필요 (실패 재시도용) | 필수 |

**결정: (a) 헤드리스 호출.** 상시 세션을 띄우지 않는다. 미니 서버가 질문마다 `claude -p`를 subprocess로 호출한다.
따라서 FR-8의 큐는 '오프라인 대기'가 아니라 '호출 실패 시 재시도' 용도로 축소된다.

## 8. 요약

Nielsen & Chuang 교재 전용 **로컬 리딩 어시스턴트**다.
브라우저가 책을 보여주고, 파일 시스템이 메시지 큐 역할을 하며, Claude Code가 답변 엔진으로 붙는다.
이 구조 덕분에 API 비용 없이 CLI에서 받던 것과 동일한 품질(책 원문 + PDF 이미지 판독 + 웹 검색)의
답변을 페이지 안에서 받을 수 있고, 세션이 꺼져 있어도 질문이 유실되지 않는다.
