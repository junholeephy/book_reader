## 모순 1: Q1의 선택지(D)와 설명이 서로 다른 아키텍처를 가리킵니다

선택하신 **문자는 D**, 적어주신 **설명은 B**입니다.

**D의 정의** (원문): "Python 백엔드를 만들고 **내 API 키로 Claude API를 호출.** 웹 검색·책 검색 도구도 직접 구현."
→ 답변하는 주체가 **내가 만든 별도 프로그램**입니다. Claude Code는 이 도구를 *만들기만* 하고, 실제 운영 중에는 관여하지 않습니다.

**적어주신 설명**: "내가 CLI에서 질의 하듯이, HTML에서의 질의를 **claude code가** PDF와 웹을 기반으로 답변하면 돼"
→ 답변하는 주체가 **Claude Code 자신**입니다. 이건 B의 정의입니다.

두 방식은 답변 주체가 다르므로 **동시에 성립할 수 없습니다.** 그리고 차이가 매우 큽니다:

| | B (Claude Code가 답변) | D (자체 에이전트가 답변) |
|---|---|---|
| 답변 주체 | Claude Code (지금 CLI에서 쓰는 그것) | 내가 만든 Python 프로그램 |
| **비용** | **0원** (기존 구독으로 커버) | **질문마다 API 토큰 과금** |
| PDF 원본 접근 | 그대로 가능 (수식·회로도 페이지를 이미지로 직접 판독) | 직접 구현 필요, 이미지 판독은 추가 작업 |
| 웹 검색 | 그대로 가능 | 검색 API 별도 계약·구현 필요 |
| 대화 맥락 | 이전 질문들을 기억 | 직접 구현 필요 |
| Claude Code 세션 | **켜져 있어야 함** | 불필요, 완전 독립 실행 |
| 구현 규모 | 뷰어 + 미니 서버 + 감시 루프 | 위 전부 + 에이전트 전체를 처음부터 |

**제가 D를 쓴 표현이 오해를 만들었을 수 있습니다.** D의 "완전히 독립 실행, 지연 짧음"이라는 장점만 보고 고르셨다면,
아래 A안이 그 장점 대부분을 비용 없이 제공합니다.

### 확인: 지연 문제는 해결됩니다

원래 B의 단점으로 "폴링 주기만큼 지연"을 적었는데, 검토 결과 **파일 감시(watch) 방식으로 즉시 감지가 가능**합니다.
질문이 들어오는 순간 Claude Code가 깨어나므로, 실질 지연은 폴링 대기가 아니라 **답변을 생각하고 책·웹을 조사하는 시간**뿐입니다.
이건 D를 골라도 똑같이 발생하는 시간입니다. 즉 **B의 지연 단점은 사실상 사라졌습니다.**

### Clarification Question 1

우측 패널의 질문에 실제로 답변할 주체는 누구입니까?

**A) Claude Code가 답변한다 (설명하신 내용 = 원래 B안, 지연 개선판)** ⭐ 추천

구성: HTML 뷰어 + 로컬 미니 서버 + Claude Code 파일 감시.
HTML에서 질문 → 서버가 질문 파일로 저장 → Claude Code가 즉시 감지 →
`refs/nc.sh`로 책 원문 검색 + 필요시 PDF 페이지 이미지 판독 + 필요시 웹 검색 → 답변 파일 작성 → 페이지에 표시.

- 비용 0원, 지금 CLI에서 받는 답변과 **완전히 동일한 품질**
- 제약: 사용할 때 Claude Code 세션이 떠 있어야 함 (터미널 창 하나를 띄워두는 정도)

**B) 자체 Python 에이전트가 답변한다 (문자 그대로의 D안)**

Anthropic API 키를 넣고 백엔드가 직접 Claude API 호출. 책 검색·웹 검색 도구도 제가 구현.

- Claude Code 없이 독립 실행 가능
- 대신 **질문마다 API 비용이 실제로 청구**되고, 구현 규모가 몇 배로 커집니다
- 이 경우 API 키 준비가 필요합니다

**C) 일단 A로 만들고, 나중에 필요하면 B로 확장한다**

서버와 HTML은 그대로 두고 "답변 생성기"만 교체 가능하도록 경계를 설계.
지금은 비용 0으로 시작하되 나중에 독립 실행이 필요해지면 그때 붙입니다.
(단, Q7에서 "개인 학습 도구, YAGNI"를 고르셨으므로 지금 당장은 A로 충분해 보입니다)

**X) Other** (직접 설명)

[Answer]: A
